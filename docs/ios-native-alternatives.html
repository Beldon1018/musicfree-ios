不照搬 Android，用 iOS 自己的形态实现：灵动岛 / 锁屏实时活动、App 内歌词浮层、AVFoundation 内嵌歌词、应用内元数据覆盖层

一、为什么不能照搬 Android

Android 做法iOS 现实结论
SYSTEM_ALERT_WINDOW 跨 App 悬浮窗，覆盖状态栏没有公开等价能力。App 只能在自己的 window 树里绘制，退到后台后更不可能覆盖别的 App形态必须改变，不能「移植」

三、逐项方案

3.1 状态栏歌词 → 前台浮层（已实现）

LyricUtilModule.m 复用 Android 侧完全相同的 JS 接口（showStatusBarLyric / setStatusBarLyricText / hideStatusBarLyric / 各种样式 setter），把「系统悬浮窗」换成 App 自己的一个透明 UIWindow：

  • 卡片可拖动（UIPanGestureRecognizer），位置/宽度/字号/对齐/颜色都从上游传来的 config 映射；同时兼容 0..1 与 0..100 两种百分比、#RRGGBB 与 Android 0xAARRGGBB 整数颜色。
  • 自定义 -hitTest:withEvent: 让卡片之外的触摸穿透到下面的 App，否则全屏 window 会让整个 MusicFree 点不动。
  • checkSystemAlertPermission 改为返回 YES（App 内浮层不需要系统权限），这样上游设置里的「开启桌面歌词」开关才真正能打开。
  • 所有 UI 操作强制主线程；window 用 UIWindowScene 初始化且不调用 makeKeyAndVisible，避免抢走 RN 的 keyWindow。
边界：浮层只在 App 前台可见，进入后台或锁屏后消失。这正是下面灵动岛那一层要补的场景，两者是互补而不是重复。

3.2 状态栏歌词 → 灵动岛 / 锁屏实时活动（已接线，随包产出）

用 ActivityKit + Widget Extension 显示当前歌词行。iOS 16.1 起所有机型在锁屏显示，iPhone 14 Pro 及以后机型额外显示在灵动岛。

接线方式变了：早期版本里这些 Swift 文件只是「源码齐备、默认不入 target」，导致 NSClassFromString(@"MFLiveActivityController") 恒为 nil、灵动岛永远空白。现在 prepare.sh 每轮会经 inject_ios.py 调用 scripts/inject_live_activity.py，幂等地往重新检出的 project.pbxproj 里写入 PBXNativeTarget、源文件引用、PBXCopyFilesBuildPhase（dstSubfolderSpec = 13，即 PlugIns）与 target 依赖 —— 因为 upstream/ 每次都会被重置，接线必须放在脚本里，不能只改一次工程文件。

第二批（v1.1.0）的状态契约：ActivityAttributes 在 request 之后不可变，早期把 title / artist 放在 attributes 里，切歌时标题永远显示写死的 "MusicFree"。现在 ContentState 承载全部 UI 状态（title / artist / lyric / translation / previousLyric / nextLyric / isPlaying / duration / elapsed），attributes 只剩不可变的 source；Swift 控制器以 applyState(_ json:) 为单一入口，RN 侧任何变更都转成一段 JSON patch。

更新链路：TrackPlayer 的 4Hz PlaybackProgressUpdated → overlay/src/native/liveActivity/index.ios.ts 状态发布器（installed guard，读取 currentMusic / currentLyricItem / 翻译开关）→ applyState JSON patch → ObjC 桥（主线程派发）→ Swift 控制器（250ms 节流、幂等 start / stop）→ Activity.update(using:)。lyricUtil/index.ios.ts 只管 App 内浮层，桌面歌词开关发 {"action":"start"} / {"action":"stop"}，不再推歌词文本，也避免和 lyricManager 形成循环依赖。

// 所有 UI 状态都在 ContentState，attributes 只剩 source
public struct ContentState: Codable, Hashable {
    var title: String;          var artist: String
    var lyric: String;          var translation: String?
    var previousLyric: String?; var nextLyric: String?
    var isPlaying: Bool;        var duration: Double
    var elapsed: Double
}
// 有活动只 update，无活动才 request；pushType: nil = 本地更新
if activities.isEmpty {
    _ = try Activity.request(attributes: ..., contentState: state, pushType: nil)
} else {
    for activity in activities { Task { await activity.update(using: state) } }
}
  • 不用推送更新：自签的未签名 IPA 拿不到可靠的 APNs 配置；UIBackgroundModes = audio 让进程在后台存活，歌词行可以持续本地更新。
  • 4Hz → ~1Hz → 250ms 节流：播放进度事件提到 0.25s，但曲目、歌词行、播放态、seek 之外的变化只在约 1Hz 心跳里写入；Swift 侧再做 250ms 最小间隔节流。既让歌词更贴声音，又不会撞 ActivityKit 的更新预算与 4 KB 状态上限。
  • 本批新增的显示能力：真实歌名 / 歌手、isPlaying 暂停态、上一句 / 当前句 / 翻译 / 下一句，以及 ProgressView(value: elapsed/duration) 进度条。进度条刻意不用 iOS 16 专属的 ProgressView(timerInterval:)：本机只有 CommandLineTools、没有 iOS SDK，无法对该 API 做类型检查，改由 1Hz 的 elapsed 驱动普通进度视图更稳。
  • 幂等与收起：start 不再 end / re-request，stop 主动 end；lyricManager.setup() 加 listenersReady 防重复注册，播放器重试不会堆叠卡片或放大歌词事件。
  • 降级路径仍然保留，但已不是默认状态：ObjC 桥用 NSClassFromString(@"MFLiveActivityController") 运行时解析 Swift 类，并把 -Swift.h 依赖彻底去掉。当前构建已接线，这个分支不会走到；只有接线脚本失效、或被人为移除 target 时才会退回静默 no-op。为防这种静默回退，verify_ipa.py 现在把「产物里没有 .appex」直接判为失败，CI 另有行为测试兜底。
自签场景的硬约束（当前包必读）：Widget Extension 是独立的 .appex，必须和 .app 一起签：先签 Frameworks/ 与 .appex，再签 .app，最后重打 Payload/，且扩展 id com.musicfree.ios.unsigned.lyrics 必须是主 id 的子前缀。AltStore / Sideloadly 默认支持；手动 codesign 需要显式签一遍（完整命令与两份 entitlements 见 《签名与闪退排查》§3.2）。不要再「把扩展删掉图省事」：那样产物会被 verify_ipa.py 判失败，且灵动岛/锁屏歌词彻底不可用。签完用 scripts/verify_signed_ipa.sh 自检，它会检查扩展是否存在且签名有效。另外用户在系统设置里关闭「实时活动」时，ActivityAuthorizationInfo().areActivitiesEnabled 为 false，控制器会安静地不启动 —— 这是预期行为，不是签名问题。

3.3 内嵌歌词读取（已实现）

此前 Mp3UtilModule.m 只读 asset.commonMetadata，因此拿不到歌词。现在遍历 asset.metadata，按 keySpace 匹配 ID3 的 USLT / SYLT、iTunes 的 ©lyr、Vorbis 的 LYRICS，并对 NSData 形式的 USLT payload 做 ID3v2 解码（编码字节 + 3 字节语言 + 描述符终止符 + 文本，支持 ISO-8859-1 / UTF-16 / UTF-8）。

上游 plugin.ts:1048 的 getLyric() 逻辑保持不变：内嵌歌词为空 → 读同名 .lrc → 都没有才交给插件在线歌词。getLyric 外层有 try/catch，解析失败只会回退，不会崩。

3.4 ID3 写入 → 应用内元数据覆盖层（已实现）

Android 用 tag.setField(...) 直接改文件；iOS 侧改成把编辑结果持久化到 Documents/musicfree_meta_overrides.json，键为标准化后的文件路径：

getBasicMeta / getMediaMeta = AVFoundation 元数据  ⊕  覆盖层
getLyric                   = 覆盖层 lyric  >  内嵌 USLT  >  ""（再由上游回退 .lrc）
getMediaTag                = 合并结果 + 内嵌歌词
setMediaTag                = 写入覆盖层（不碰音频文件）

这里有个容易被忽略的事实：全仓检索 setMediaTag / getMediaTag，上游 TS/UI 层没有任何调用点，只有接口声明和 Android 原生实现。也就是说「ID3 写入」在 Android 版里也还没接进界面。所以把能力做在 Pod 内部、让现有读取接口直接生效，比补一个没人调用的写入 API 更有意义；将来若要加「编辑歌曲标签」的 UI，直接调 setMediaTag 即可。
