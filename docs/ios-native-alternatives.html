一、为什么不能照搬 Android

Android 做法iOS 现实结论
SYSTEM_ALERT_WINDOW 跨 App 悬浮窗，覆盖状态栏没有公开等价能力。App 只能在自己的 window 树里绘制，退到后台后更不可能覆盖别的 App形态必须改变，不能「移植」
jaudiotagger 用 AudioFileIO.read() + commit() 写 ID3AVFoundation 只读元数据、不提供 ID3 写回；自写 frame 写入器会改写用户的音频文件，在沙盒里既危险又容易损坏换成应用内覆盖层
jaudiotagger 读 FieldKey.LYRICSAVFoundation 的 asset.metadata 能读 ID3v2 USLT/SYLT（此前误判为「无公开 API」，已纠正）可以等价实现
锁屏 / 状态栏逐行歌词MPNowPlayingInfoCenter 无法放逐行歌词；Apple Music 的锁屏逐行歌词是私有能力。Live Activity 是唯一的公开路径用灵动岛 / 锁屏实时活动

三、逐项方案

3.1 状态栏歌词 → 前台浮层（已实现）

LyricUtilModule.m 复用 Android 侧完全相同的 JS 接口（showStatusBarLyric / setStatusBarLyricText / hideStatusBarLyric / 各种样式 setter），把「系统悬浮窗」换成 App 自己的一个透明 UIWindow：

  • 卡片可拖动（UIPanGestureRecognizer），位置/宽度/字号/对齐/颜色都从上游传来的 config 映射；同时兼容 0..1 与 0..100 两种百分比、#RRGGBB 与 Android 0xAARRGGBB 整数颜色。
  • 自定义 -hitTest:withEvent: 让卡片之外的触摸穿透到下面的 App，否则全屏 window 会让整个 MusicFree 点不动。
  • checkSystemAlertPermission 改为返回 YES（App 内浮层不需要系统权限），这样上游设置里的「开启桌面歌词」开关才真正能打开。
  • 所有 UI 操作强制主线程；window 用 UIWindowScene 初始化且不调用 makeKeyAndVisible，避免抢走 RN 的 keyWindow。
边界：浮层只在 App 前台可见，进入后台或锁屏后消失。这正是下面灵动岛那一层要补的场景，两者是互补而不是重复。

3.2 状态栏歌词 → 灵动岛 / 锁屏实时活动（源码齐备，可选接线）

用 ActivityKit + Widget Extension 显示当前歌词行。iOS 16.1 起所有机型在锁屏显示，iPhone 14 Pro 及以后机型额外显示在灵动岛。

组成文件归属 target
活动数据模型MusicFreeLyricAttributes.swift主 App + Extension
ActivityKit 控制器（启动 / 更新 / 结束 / 节流）MusicFreeLiveActivityController.swift主 App
SwiftUI 界面（锁屏 + 灵动岛 compact/expanded/minimal）MusicFreeLiveActivityWidget.swiftExtension
Extension 配置LiveActivity/Info.plist（NSExtensionPointIdentifier = com.apple.widgetkit-extension）Extension
RN 桥MusicFreeLiveActivityModule.{h,m}本地 Pod（默认已编译）

更新链路：lyricManager.ts 的 PlaybackProgressUpdated → LyricUtil.setStatusBarLyricText → index.ios.ts 联动 NativeModules.MusicFreeLiveActivity.updateLyric → ObjC 桥 → Swift 控制器 → Activity.update(using:)。

// 关键取舍：本地更新，不用 APNs
let state = MusicFreeLyricAttributes.ContentState(
    lyric: lyric, previousLyric: nil, isPlaying: true)
for activity in Activity<MusicFreeLyricAttributes>.activities {
    Task { await activity.update(using: state) }
}
  • 不用推送更新：自签的未签名 IPA 拿不到可靠的 APNs 配置；UIBackgroundModes = audio 让进程在后台存活，歌词行可以持续本地更新。
  • 1 秒节流 + 相同文本去重：ActivityKit 有更新预算，逐行歌词（几秒一行）完全够用，也远低于 4 KB 状态上限。
  • 自动降级：ObjC 桥用 NSClassFromString(@"MFLiveActivityController") 运行时解析 Swift 类，并把 -Swift.h 依赖彻底去掉。没接 Widget Extension 时，每次调用都是静默 no-op，默认 IPA 构建完全不受影响。
自签场景的硬约束：Widget Extension 是独立的 .appex，必须和 .app 一起签（先签 appex，再签 app，再重打 Payload/）。AltStore 支持；手动 codesign 或部分自签工具可能不支持。若不支持，就不要加这个 target —— 前台浮层仍可用，RN 桥会自动降级。另外用户在系统设置里关闭「实时活动」时，ActivityAuthorizationInfo().areActivitiesEnabled 为 false，控制器会安静地不启动。

3.3 内嵌歌词读取（已实现）

此前 Mp3UtilModule.m 只读 asset.commonMetadata，因此拿不到歌词。现在遍历 asset.metadata，按 keySpace 匹配 ID3 的 USLT / SYLT、iTunes 的 ©lyr、Vorbis 的 LYRICS，并对 NSData 形式的 USLT payload 做 ID3v2 解码（编码字节 + 3 字节语言 + 描述符终止符 + 文本，支持 ISO-8859-1 / UTF-16 / UTF-8）。

上游 plugin.ts:1048 的 getLyric() 逻辑保持不变：内嵌歌词为空 → 读同名 .lrc → 都没有才交给插件在线歌词。getLyric 外层有 try/catch，解析失败只会回退，不会崩。

3.4 ID3 写入 → 应用内元数据覆盖层（已实现）

Android 用 tag.setField(...) 直接改文件；iOS 侧改成把编辑结果持久化到 Documents/musicfree_meta_overrides.json，键为标准化后的文件路径：

getBasicMeta / getMediaMeta = AVFoundation 元数据  ⊕  覆盖层
getLyric                   = 覆盖层 lyric  >  内嵌 USLT  >  ""（再由上游回退 .lrc）
getMediaTag                = 合并结果 + 内嵌歌词
setMediaTag                = 写入覆盖层（不碰音频文件）

这里有个容易被忽略的事实：全仓检索 setMediaTag / getMediaTag，上游 TS/UI 层没有任何调用点，只有接口声明和 Android 原生实现。也就是说「ID3 写入」在 Android 版里也还没接进界面。所以把能力做在 Pod 内部、让现有读取接口直接生效，比补一个没人调用的写入 API 更有意义；将来若要加「编辑歌曲标签」的 UI，直接调 setMediaTag 即可。
