签名后打开闪退：诊断、修复与正确自签步骤

为什么构建成功 ≠ 真机能启动；哪些问题已在源码侧修掉，哪一步必须由签名工具做对

2026-11-12 更新 上游 v1.0.0-beta.4 启动修复 c8a13af 静态校验 69/69 含 Widget Extension (.appex) 适用：未签名 IPA 自签
一句话结论：「打开即闪退」有两类独立原因，必须同时处理。

主因（已在源码侧修复，有 Expo 源码级证据）：Expo SDK 52 在原生启动阶段执行 SplashScreenAppDelegateSubscriber.customizeRootView → SplashScreenManager.initWith → showSplashScreen → UIStoryboard(name: "SplashScreen", bundle: nil)。 UIStoryboard(name:) 找不到同名 storyboard 会直接抛异常。而上游 RN 模板只有 LaunchScreen.storyboard，ExpoSplashScreen.podspec 也不带任何 storyboard 资源 —— 旧包里根本没有 SplashScreen.storyboardc，所以 App 在 React Native 挂载之前就被杀掉。这跟 JS 里有没有调用 SplashScreen 无关。

另一类（签名侧，必须做对）：包内有 Frameworks/hermes.framework。自签工具若只签主可执行文件，dyld 加载 Hermes 时校验失败，同样会在 main() 之前终止进程。换新包也不能省掉这一步。

2026-11-12 追加（当前包必读）：灵动岛 / 锁屏歌词的 Widget Extension 已经接线，产物内含 PlugIns/MusicFreeLiveActivity.appex。它不是资源文件，而是第二个需要独立签名的可执行体：必须先签 .appex 和嵌套 framework，再签 .app，否则轻则安装被拒，重则灵动岛静默失效。下面第 3 节已按新包结构重写。

2. 修复过程（三次尝试，如实记录）

第一次尝试 a4f3d63 只是把被删掉的 LaunchScreen.storyboard 恢复回来。云端 run 42853265361 构建失败、没有出包：日志里 ibtool 命令根本没有 --platform 参数（旁边的 actool 却有 --platform iphoneos），依旧报 LaunchScreen.storyboard: error: iOS 18.2 Platform Not Installed.。这证明早期「加 -sdk iphoneos 就够了」的推断是错的。追到 Expo 源码后又发现，即便编译成功，文件名 LaunchScreen 也不满足 Expo 要的 SplashScreen。

第二次尝试 f70b008 从 Expo 的硬编码名字出发重构启动屏：

修复内容与理由
提供 Expo 要的 storyboard inject_ios.py 从上游 LaunchScreen.storyboard 生成一份最小的 SplashScreen.storyboard，把 pbxproj 中 7 处 LaunchScreen.storyboard 的文件名字符串改为 SplashScreen.storyboard（对象结构不变），并设 UILaunchStoryboardName = SplashScreen。系统启动屏与 Expo 的 UIStoryboard(name:) 因此指向同一份编译产物 SplashScreen.storyboardc。
修掉 CI 的 ibtool 报错 生成时移除旧 RN 模板 XML 的 <dependencies>（内含 <deployment identifier="iOS"/>）和 <device>，并把 toolsVersion 刷新为 22505。这段旧元数据正是 ibtool 去查找不存在的「iOS 18.2」平台的来源。保留原有 scene、label 与约束，XML 解析校验通过。
iOS 跳过 Android 权限 把 bootstrap.ts 的 } else { 改为 } else if (Platform.OS === "android") {，iOS 不再调用 check/request(PERMISSIONS.ANDROID.READ_EXTERNAL_STORAGE) 等常量。iOS 本来就不需要存储权限。
顶层 StatusBar 调用加保护 src/entry/index.tsx 在 React 挂载前、JS bundle 求值时就调用两个 Android-only API。改为包在 if (Platform.OS === "android") { … } 内，并补 Platform 导入，避免最早期 JS 执行被打断。
校验器加护栏 当时把 verify_adaptation.py 扩到 41 项，断言 Expo storyboard 名字、ibtool 安全的 XML 与两处启动门控；verify_ipa.py 现在缺少 SplashScreen.storyboardc 就直接判失败，并打印需要递归签名的嵌套 framework 清单。用新校验器跑旧包确实报 VERIFY FAILED。此后校验继续扩到 69 项，并新增「缺 .appex 或 NSExtensionPointIdentifier 错误即硬失败」以及 scripts/selftest_verify_ipa.py 行为测试（故意删掉 PlugIns/ 的假包必须被拒收）。
当时的本地复验：prepare.sh → 41 checks, 0 failures；生成的 SplashScreen.storyboard 通过 XML 解析（1 个 scene、无 dependencies/device），plutil -lint 校验 project.pbxproj 与 Info.plist 通过；ruby -c、py_compile、bash -n、TypeScript 5.7.3 transpileModule 全部通过。当前基线为 69 项 0 失败，且 CI 额外用 scripts/check_injected_ts.js 对 9 个注入后的 TS/TSX 做语法检查。

3. 签名侧：这一步做不对，换了新包一样闪退

最常见的错误：只重签 MusicFree.app 主程序，忽略 Frameworks/hermes.framework。未签名 IPA 里的每个动态框架都是无签名的，iOS 在启动时由 dyld 逐个校验；任何一个没有有效签名，进程会在 main() 之前被杀，用户看到的就是「图标点一下、白屏一下、回到桌面」，没有任何错误弹窗。

当前包还多一层：PlugIns/MusicFreeLiveActivity.appex 是独立的 Widget Extension，同样是未签名状态。它不签不会让主程序闪退，但会让 iOS 拒绝安装，或装上了灵动岛/锁屏歌词永远不出现 —— 后者更难自查，因为 App 本身能正常打开。签名顺序必须是 frameworks → .appex → .app。

3.1 用签名工具（推荐，最少踩坑）

  • Sideloadly / AltStore：默认会遍历并递归签名 Frameworks/ 与 PlugIns/，一般无需额外设置。若 Sideloadly 里开了自定义选项，确认没有勾选「跳过动态库签名」「忽略扩展」之类项。
  • 手机端签名工具（ESign、牛蛙助手、轻松签等）：必须确认「签名 Frameworks / 动态库 / 递归签名」和「签名 App Extension / 插件」都已开启。这类工具在只签主程序时最容易出问题。
  • 扩展 id 不能被落下：主程序是 com.musicfree.ios.unsigned，Widget Extension 是 com.musicfree.ios.unsigned.lyrics（必须是主 id 的子前缀）。很多自动签名工具会把主 id 改成自己的通配 id，此时必须把扩展 id 一起改，并且两份 entitlements 的 application-identifier 分别对应各自 id，否则常见结果是「主 App 装上了、灵动岛没反应」或安装直接被拒。
  • 最低系统要求：主 App iOS 15.1；灵动岛 / 锁屏实时活动要求 iOS 16.1+（灵动岛形态还需 iPhone 14 Pro 及以后机型），低版本上实时活动会安静地不启动，主 App 不受影响。
先自检，别靠猜：适配工程里带了 scripts/verify_signed_ipa.sh，在 macOS 上对签完的 IPA 跑一次即可确认框架有没有签上： 
bash scripts/verify_signed_ipa.sh MusicFree-signed.ipa
它会逐个检查 Frameworks/*.framework、PlugIns/*.appex，再做一次 codesign --verify --deep --strict；包里一个 .appex 都没有也会直接判失败（防止签名工具把扩展整个丢掉）。拿未签名的原始包实测，输出就是 [FAIL] framework NOT signed : hermes.framework — code object is not signed at all，正是最容易导致闪退的那种状态。

3.2 手动 codesign（macOS，需要 Xcode 或 CommandLineTools）

顺序不能反：先签嵌套 framework 和每一个 .appex，再签 .app，最后打包。--deep 虽然省事，但 Apple 不推荐，手动逐个更可靠。扩展必须在主程序之前签，因为 .app 签名会把整个 bundle 的 sealing 固定下来。

# 0. 准备：把签名身份换成你自己的证书
IDENTITY="Apple Development: Your Name (TEAMID)"
ENT=entitlements-app.plist       # 主 App，见下方
ENT_EXT=entitlements-ext.plist   # Widget Extension，见下方
unzip -q MusicFree-v1.0.0-beta.4-unsigned.ipa -d work
cd work/Payload

# 1. 放入与证书 / bundle id 匹配的描述文件（通配 profile 可两份共用）
cp /path/to/app.mobileprovision MusicFree.app/embedded.mobileprovision
cp /path/to/ext.mobileprovision \
   MusicFree.app/PlugIns/MusicFreeLiveActivity.appex/embedded.mobileprovision

# 2. 【关键】逐个签嵌套 framework —— 漏掉就会启动闪退
find MusicFree.app/Frameworks -type d -name "*.framework" -print0 |
while IFS= read -r -d '' fw; do
  codesign --force --sign "$IDENTITY" \
    --timestamp none --generate-entitlement-der "$fw" || exit 1
done

# 3. 【关键】逐个签 .appex —— 必须在 .app 之前
for ext in MusicFree.app/PlugIns/*.appex; do
  codesign --force --sign "$IDENTITY" \
    --entitlements "$ENT_EXT" --timestamp none \
    --generate-entitlement-der "$ext" || exit 1
done

# 4. 最后签整个 .app（带入主 App 的 entitlements）
codesign --force --sign "$IDENTITY" \
  --entitlements "$ENT" --timestamp none \
  --generate-entitlement-der MusicFree.app

# 5. 自检：必须全部通过
codesign --verify --deep --strict --verbose=2 MusicFree.app
codesign -d --entitlements - MusicFree.app
codesign -d --entitlements - MusicFree.app/PlugIns/MusicFreeLiveActivity.appex

# 6. 重新打包成可安装的 ipa（保留 PlugIns/，不要只打包可执行文件）
cd .. && zip -qry ../MusicFree-signed.ipa Payload

# 7. 回到工程根目录，用脚本再验一次（含「扩展是否被丢掉」检查）
bash scripts/verify_signed_ipa.sh path/to/MusicFree-signed.ipa

两份 entitlements 示例（TEAMID 换成你自己的 Team ID，两个 application-identifier 必须与各自的描述文件一致）。只给主 App 写一份是最常见的漏项 —— 扩展会因此签不上或装上后不工作：

entitlements-app.plist · 主 App com.musicfree.ios.unsigned

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" ...>
<plist version="1.0">
<dict>
  <key>application-identifier</key>
  <string>TEAMID.com.musicfree.ios.unsigned</string>
  <key>com.apple.developer.team-identifier</key>
  <string>TEAMID</string>
  <key>get-task-allow</key>
  <true/>
</dict>
</plist>

entitlements-ext.plist · Widget Extension com.musicfree.ios.unsigned.lyrics

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" ...>
<plist version="1.0">
<dict>
  <key>application-identifier</key>
  <string>TEAMID.com.musicfree.ios.unsigned.lyrics</string>
  <key>com.apple.developer.team-identifier</key>
  <string>TEAMID</string>
  <key>get-task-allow</key>
  <true/>
</dict>
</plist>
如果签名工具自动改了 bundle id：例如主 id 变成 TEAMID.com.yourname.MusicFree，扩展 id 必须同步改成它的子前缀（…MusicFree.lyrics 之类），并把上面四个字符串里的 id 全部替换。扩展 id 不是主 id 的子前缀时，iOS 会拒绝安装。本扩展不需要 App Group、推送或任何特殊 entitlement（实时活动走本地更新、pushType: nil），个人免费证书即可。

4. 如果换了修复版、也按上面签了，仍然闪退

那就必须靠崩溃日志定位，静态分析到此为止。请按下面任一方式取日志：

1
iPhone 上直接导出（最方便） 设置 → 隐私与安全性 → 分析与改进 → 分析数据，找以 MusicFree 开头、时间为刚才的 .ips 文件，导出后发我。
2
macOS「控制台」App 设备连上 Mac，打开「控制台」，左侧选设备，筛选进程名 MusicFree，复现闪退，导出对应时段的日志。
3
命令行实时日志 idevicesyslog（libimobiledevice）或 xcrun deviceconsole，复现一次即可抓到 dyld / 异常栈。

日志里重点看这几类关键字，它们分别指向不同修复方向：

关键字含义 / 下一步
